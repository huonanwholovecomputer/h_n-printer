## 一、本轮小程序改了什么

改动文件：`mobile_apps/h_n_print/pages/index/index.js`

### 1）上传中删文件导致结果写错卡片（审计 🔴6）

**修复的问题**：上传过程中删除**前面的**文件后，后面文件的上传结果会落到错误的卡片上。

具体机制（旧版）：

1. `startFileUpload(fileIndex, ...)` 在开始时把下标拼成字符串路径
   `const key = 'selectedFiles[' + fileIndex + ']'`，之后所有 `setData` 都用这个**闭包里的旧下标**；
2. `onRemoveFile` 在卡片退场动画（600ms）后 `files.splice(index, 1)` —— 其后元素**全部前移**；
3. 于是「B 文件的上传成功回调」在数组已变成 `[A, C]` 之后触发时，仍按旧下标 1 写入
   → **B 的 `file_id`/页数写到了 C 的卡片上**；
4. 提交订单时按卡片字段拼参数 → **打印的是另一个文件的内容、按另一个文件的页数计价**。

旧版还有一段 `remapTimers` 只重映射了 `_uploadTimers`/`_pollTimers` 两个表，
但 `setData` 路径仍用闭包旧下标，所以只修了一半；而且它按「下标」作键，本身就是错配来源。

修复后：

- 每个文件携带稳定身份 `_uid`（新增文件、重印恢复两条路径都赋值）；
- 上传/轮询计时器一律以 `_uid` 为键（下标变动天然不影响，删除元素后**不再需要 remap**）；
- 所有异步回调（`success`/`fail`/进度定时器/页数轮询）都调 `_fileIndexByUid(uid)` **现算当前下标**；
- 文件已被删除（`_fileIndexByUid` 返回 -1）→ **整份结果丢弃**，绝不写到任何卡片上；
- 页数轮询额外校验 `fileId` 未变（防「删除后重新添加同名文件」时串台）。

### 2）页码范围解析与后端对齐（计费显示一致）

旧版 `countPagesInRange` 与后端 `_count_pages_in_range` 有三处口径偏差，导致
**提交前显示价 ≠ 提交后实收价**：

| 偏差 | 旧前端 | 后端 | 实测后果 |
|---|---|---|---|
| 空白 | 替换成逗号 | **删除** | 3 页文档填 `1 - 3`、双面 1 份 → 前端显示 ¥0.40，**后端实收 ¥0.70** |
| 整数解析 | `parseInt`（宽容） | `int()`（严格） | `3a` 前端认成第 3 页；后端判非法 → 整段无效 → 退回**全份**计费 |
| 段内 `-` | `split('-')` 全切 | `split('-', 1)` 只切一刀 | `1-2-3` 前端认成 1-2 |

修复后前端逐字对齐后端语义（空白删除、严格整数、只切一刀），非空但全无效时同样退回全份。
另把迭代区间收窄到 `[1, total]`（结果集合不变，但 `1-999999999` 这类输入不再卡死）。

### 3）派送费取整与后端对齐（差 1 分）

后端 `round(文件费 × pct / 100, 2)` **先取整再相加**，前端原先「先相加、最后 `toFixed(2)`」。
实测文件费 ¥0.30 + 派送 5% → 后端实收 ¥0.31、前端显示 ¥0.32（10%/20% 恰好整除，不受影响）。

修复后前端用 `pyRound2()` —— 一个与 Python `round(x,2)` **同口径**的取整（按 IEEE754 精确十进制展开 + 半偶进位）。
为什么不能直接用 `Math.round(x*100)/100` 或 `toFixed(2)`：在「真值恰落在 .xx5 边界、double 落点偏向另一侧」时会差 1 分。
线上定价下 1020 组可达输入的实测不一致数：`Math.round` 63 组、`toFixed` 6 组、`pyRound2` **0 组**
（选型脚本：`tests/_pick_js_rounding.py`）。

## 二、发版步骤

1. 微信开发者工具打开 `mobile_apps/h_n_print/`（appid `wx3b1e5b97ac1a6511`）。
2. **发布前务必确认 `utils/config.local.js` 存在且 `BASE_URL` 为 `https://hn-space.cn`**。
   该文件被 git 忽略但**会随小程序一起上传**；一旦缺失，`utils/config.js` 会退回占位符
   `https://your-server.com`，线上小程序全部接口都会失败。这是本目录最容易踩的坑。
3. 开发者工具「上传」→ 填版本号与项目备注。
4. 微信公众平台 → 版本管理 → 提交审核 → 审核通过后「发布」。
5. 发布后建议在**真机**上过一遍第三节的自测清单（开发者工具的模拟器对 `setData`/异步时序不敏感，
   有些竞态只在真机 + 真实网络下才出现）。

## 三、真机自测清单（按风险从高到低）

每个用例都要选**较大的文件**（几 MB）以保证上传有足够的耗时窗口，并在上传进度条还没走完时操作。

| # | 用例 | 期望结果 |
|---|------|----------|
| 1 | 选 A、B、C 三个文件；等 B 的进度条走到一半时删除 B；等 A、C 上传完成 | A、C 卡片各自显示**自己**的页数与状态；不存在某个卡片显示「另一个文件的页数」 |
| 2 | 接用例 1，直接提交订单 | 订单明细里**文件名 ↔ 页数 ↔ 金额**三者对应正确（重点看 C 的页数是不是 C 自己的） |
| 3 | 删除**第一个**文件（索引 0），保留后面两个继续上传 | 剩下的文件仍能正常确认页数（不出现某个卡片永远停在「等待中/分析中」） |
| 4 | 连续快速删除两个文件（B、C） | 不出现页数为 0 却已「已确认」的卡片；不出现进度条卡在半路 |
| 5 | 上传中删掉一个 **doc/docx**（页数未知，走轮询） | 剩余 doc/docx 的页数能被正常确认；不出现「等待本地打印工具」永久转圈 |
| 6 | 整份 1 页的 PDF/Word | 模式行隐藏、提交强制单面（`singlePage` 判定未被破坏） |
| 7 | 「重印」入口恢复一批文件（含页数未知的） | 已带 `file_id` 的文件不重新上传；页数未知的能正常轮询确认 |
| 8 | 提交成功后关闭成功弹窗 | 文件列表清空，不残留任何进度条/轮询（计时器已随 `_onCloseModal` 停掉） |
| 9 | **范围行输入 `1 - 3`（数字间带空格）**，文档 ≥3 页 | 页数摘要与金额按 **3 页**计（旧版会按 2 页算，比实收低） |
| 10 | 选「图书馆 15%」或「1号楼南楼 5%」派送，观察总价 | 提交前显示的总价与提交后订单金额**逐分一致**（旧版可能差 1 分） |

**回归重点**：用例 1–3、9、10 在**旧版本上会失败**，是本次修复的靶心；用例 4–8 是防止改坏原有功能。

## 四、本轮核对新发现、尚未修（供下一轮评估）

均为 `python tests/verify_pricing_consistency.py` 的输出，**不是 FAIL**，但值得排期：

1. **超长页码范围会长时间占满 CPU**（建议优先）
   后端 `_parse_page_range_set` 与本地 `_parse_range_parts` 都是 `for p in range(start, end+1)`
   全区间遍历、遍历中才过滤 —— 实测 1e6 区间约 20ms，线性外推 `1-999999999` 约 **20 秒**；
   已登录用户提交该 `page_range` 即可长时间占用一个 gunicorn worker，几个并发就能拖垮服务。
   前端 `parseSingleRange` 同病且把页号塞进**无上限 Set**（1e6 用 79ms，1e9 约 79 秒且内存爆掉），
   用户手输超长区间会卡死自己的界面。
   修法与本轮 `countPagesInRange` 一致：迭代前把 `start/end` 收窄到 `[1, total]`，**结果集合完全不变**。
2. **单价若取到 3 位小数**（如 `0.335`），后端与前端会差 1 分（160 组）。现价 `0.3/0.4` 是 2 位小数，
   暂无影响；建议在「收支统计 → 设置」的单价输入处限制 2 位小数。
3. **张数口径不同**：结算页 `_fileSheets` 按**整份页数**折算（注释写明与「总页数」口径一致），
   后端 `_file_range_stats` 按**页码范围**折算。例：2 页文档范围填 `2` → 结算页 2 张 vs 后端 1 张。
   两者都不算错，但对账时容易被误读为不一致，建议在结算页标注口径。
4. **全角数字**（如 `０１`）：Python `int()` 认，JS 严格 ASCII 不认。
   已验证**不可达** —— 前端行校验 `parseSingleRange` 用 `parseInt`，同样不认全角，该行会被判非法。
   仅作记录，无需处理。
