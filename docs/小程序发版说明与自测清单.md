# 微信小程序发版说明与自测清单

> 适用：本次修复 `mobile_apps/h_n_print/pages/index/index.js`（上传中删文件导致结果写错卡片）。
> 小程序**没有自更新通道**，仓库改完不等于线上生效，必须手工上传发布。

## 一、本轮小程序改了什么

**唯一改动文件**：`mobile_apps/h_n_print/pages/index/index.js`

**修复的问题**：上传过程中删除**前面的**文件后，后面文件的上传结果会落到错误的卡片上。

具体机制（旧版）：

1. `startFileUpload(fileIndex, ...)` 在开始时把下标拼成字符串路径
   `const key = 'selectedFiles[' + fileIndex + ']'`，之后所有 `setData` 都用这个**闭包里的旧下标**；
2. `onRemoveFile` 在卡片退场动画（600ms）后 `files.splice(index, 1)` —— 其后元素**全部前移**；
3. 于是「B 文件的上传成功回调」在数组已变成 `[A, C]` 之后触发时，仍按旧下标 1 写入
   → **B 的 `file_id`/页数写到了 C 的卡片上**；
4. 提交订单时按卡片字段拼参数 → **打印的是另一个文件的内容、按另一个文件的页数计价**。

旧版还有一段 `remapTimers` 只重映射了 `_uploadTimers`/`_pollTimers` 两个表，
但 `setData` 路径仍用闭包旧下标，所以只修了一半；而且它按「下标」作键，本身就是错配来源。

修复后：

- 每个文件携带稳定身份 `_uid`（新增文件、重印恢复两条路径都赋值）；
- 上传/轮询计时器一律以 `_uid` 为键（下标变动天然不影响，删除元素后**不再需要 remap**）；
- 所有异步回调（`success`/`fail`/进度定时器/页数轮询）都调 `_fileIndexByUid(uid)` **现算当前下标**；
- 文件已被删除（`_fileIndexByUid` 返回 -1）→ **整份丢弃结果**，绝不写到任何卡片上；
- 页数轮询额外校验 `fileId` 未变（防「删除后重新添加同名文件」时串台）。

### 验证方式（无需手工即可复现）

```bash

node tests/audit_2026_12/verify_frontend_legacy.js   # 反证：旧版确实把 B 的 file_id 写到 C（复现 bug）
```

## 二、发版步骤

1. 微信开发者工具打开 `mobile_apps/h_n_print/`（appid `wx3b1e5b97ac1a6511`）。
2. **发布前务必确认 `utils/config.local.js` 存在且 `BASE_URL` 为 `https://hn-space.cn`**。
   该文件被 git 忽略但**会随小程序一起上传**；一旦缺失，`utils/config.js` 会退回占位符
   `https://your-server.com`，线上小程序全部接口都会失败。这是本目录最容易踩的坑。
3. 开发者工具「上传」→ 填版本号与项目备注。
4. 微信公众平台 → 版本管理 → 提交审核 → 审核通过后「发布」。
5. 发布后建议在**真机**上过一遍第三节的自测清单（开发者工具的模拟器对 `setData`/异步时序不敏感，
   有些竞态只在真机 + 真实网络下才出现）。

## 三、真机自测清单（按风险从高到低）

每个用例都要选**较大的文件**（几 MB）以保证上传有足够的耗时窗口，并在上传进度条还没走完时操作。

| # | 用例 | 期望结果 |
|---|------|----------|
| 1 | 选 A、B、C 三个文件；等 B 的进度条走到一半时删除 B；等 A、C 上传完成 | A、C 卡片各自显示**自己**的页数与状态；不存在某个卡片显示「另一个文件的页数」 |
| 2 | 接用例 1，直接提交订单 | 订单明细里**文件名 ↔ 页数 ↔ 金额**三者对应正确（重点看 C 的页数是不是 C 自己的） |
| 3 | 删除**第一个**文件（索引 0），保留后面两个继续上传 | 剩下的文件仍能正常确认页数（不出现某个卡片永远停在「等待中/分析中」） |
| 4 | 连续快速删除两个文件（B、C） | 不出现页数为 0 却已「已确认」的卡片；不出现进度条卡在半路 |
| 5 | 上传中删掉一个 **doc/docx**（页数未知，走轮询） | 剩余 doc/docx 的页数能被正常确认；不出现「等待本地打印工具」永久转圈 |
| 6 | 整份 1 页的 PDF/Word | 模式行隐藏、提交强制单面（`singlePage` 判定未被破坏） |
| 7 | 「重印」入口恢复一批文件（含页数未知的） | 已带 `file_id` 的文件不重新上传；页数未知的能正常轮询确认 |
| 8 | 提交成功后关闭成功弹窗 | 文件列表清空，不残留任何进度条/轮询（计时器已随 `_onCloseModal` 停掉） |

**回归重点**：用例 1–3 在**旧版本上会失败**，是本次修复的靶心；用例 4–8 是防止改坏原有功能。

## 四、与本次小程序改动相关的待修问题（下一轮，尚未修）

计费核对（`python tests/verify_pricing_consistency.py`）发现两处**前端与后端口径不一致**，
小程序端同样存在，建议与本次发版一并评估：

1. **页码范围含空格时前端低估页数**（`1 - 3`）
   后端把空白**删除**（`1 - 3` → 1-3 → 3 页），前端把空白**替换成逗号**（→ `1,-,3` → 只认 1 与 3 → 2 页）。
   实测：3 页文档填 `1 - 3`、双面 1 份 → 后端实收 ¥0.70，前端显示 ¥0.40（差 ¥0.30）。
   前端 `parseSingleRange` 用 `parseInt` 剥空白，所以 `1 - 3` 被判为**合法输入**，此路径真实可达。
   复现脚本：`python tests/verify_range_space_divergence.py`
2. **派送费取整时机不一致**（5%、15% 两档）
   后端 `round(文件费×pct/100, 2)` 先取整再相加；前端先相加最后 `toFixed(2)`。
   实测：文件费 ¥0.30 + 派送 5% → 后端实收 ¥0.31，前端显示 ¥0.32（差 1 分）。
   10%/20% 恰好整除，不受影响。
