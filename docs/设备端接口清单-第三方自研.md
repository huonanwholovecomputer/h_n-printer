# HN 打印系统 · 设备端接口清单（第三方自研设备端）

> 面向：自研设备端程序的开发者
> 依据：仓库 master 源码（`mobile_apps/printer-backend/app.py`、`local_print_tool/`）
> 目标场景：**跨订单积单** —— 任务 1..n 各自只打第一面，全部攒着；人回来后把整叠纸放回进纸盒，**一次性打完所有任务的所有背面**。

---

## 0. 先划清一件事：这个模型里"谁是权威"

他的流程与传统"一个订单一次翻面"有本质区别：

```
任务1(文件1,2) → 只打第一面 → 攒着
任务2(文件3,4) → 只打第一面 → 攒着          ← 期间新订单不断进来
...
任务n(文件t..) → 只打第一面 → 攒着
        ↓  （人回来，整叠纸一起放回进纸盒）
   一次性打印【全部任务】的所有背面 → 各任务 sent
```

由此产生一条**贯穿全文的设计原则**：

> **第一面出纸后那叠纸的物理顺序，是设备端的事实，服务器不知道也不该知道。**
> 因此"待打第二面"的账本**必须以设备端为权威**；服务器只负责三件事：
> ① 别把等待中的任务判失败/重发；② 用户取消时如实通知他；③ 让他能重新拿到源文件。

服务器若以"任务列表"当第二面的依据，一旦发生取消/失败/重发，**物理叠序就会错位，整本报废**。

## 1. 现有可用接口（现状即可对接，服务器无需改动）

### 1.1 鉴权与连接

| 项 | 现状 |
|---|---|
| REST 鉴权 | 每个设备端接口都要 printer token：`?token=<TOKEN>` 或 JSON body 里的 `token`。**当前是全局唯一 TOKEN**（后端 `config.py` 的 `TOKEN`），与官方本地工具共用 |
| 失败表现 | HTTP 403 `{"success": false, "message": "token 无效"}` |
| SocketIO 连接 | `/?token=<TOKEN>&client_id=<id>&device_name=<名>&printer_name=<队列名>&printer_driver=<驱动>&printer_port=<端口>&auto_duplex=<true|false>` |
| 连接失败 | 服务端 emit `auth_fail` `{message}` |

### 1.2 身份与设备管理

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/printer/claim` | 启用接单。body `{client_id, device_name}`。多设备可同时启用；移动端下单时选择目标设备 |
| POST | `/api/printer/release` | 关闭接单。body `{client_id}` |
| GET | `/api/printer/devices` | 全部设备：计算机名/在线/所有者/是否接单/`auto_duplex`/`capability_source`/`capability_verified_*`/`capability_probe` |
| GET | `/api/claiming_devices` | 可接单设备列表（移动端据此选设备、判"需人工翻纸"） |
| POST | `/api/printer/capability` | 写设备能力。body `{client_id, auto_duplex, source: manual\|probe, printer_name/printer_driver/printer_port, by}` |
| POST | `/api/printer/bind_owner` | 绑定所有者（成员姓名）。body `{client_id, owner_name}` |
| POST | `/api/printer/devices/delete` | 删除设备条目 |
| POST | `/api/printer/devices/cleanup` | 清理测试/无主离线设备（默认 `dry_run`） |

`client_id` 规则：非空、**≤64 字符**、可自定义（如 `agent-lj1020-home`）。同一 `client_id` 重复连接会顶掉旧连接。**他必须固定使用同一个 `client_id`**（原因见 §3-R2、§4-1）。

### 1.3 任务获取

| 通道 | 接口 / 事件 | 说明 |
|---|---|---|
| HTTP 拉取 | `GET /api/pull_queued_orders?client_id=&device_name=` | **原子锁定，每次只返回 1 条**。仅"启用接单"的设备可领（否则返回空）。顺带登记设备 + 刷新心跳 |
| SocketIO 推送 | `print_task` | 服务端主动推（普通单 `queued → printing`；预约单阶段① `scheduled → downloading`） |
| SocketIO 推送 | `start_print` | 预约单到点兜底 `{order_id, task_ids, scheduled_ts}` |
| SocketIO 推送 | `printer_state` | 本机 `owner_name` 等状态变更 |
| SocketIO 推送 | `storage_config_updated` | 存储/保留策略变更 |
| SocketIO 推送 | `request_log` | 服务端要求上报本机日志（配合"日志管理"） |

`print_task` 载荷关键字段：
`type, task_id(=order_files.id), order_id, order_number, file_url, file_name, source_md5, auto_print, schedule_mode, scheduled_at, scheduled_ts, schedule_frozen, options{copies, duplex, page_range, image_orientation}`

`/api/pull_queued_orders` 返回体还额外带：
`id, file_id, duplex, image_orientation, task_id, delivery_enabled, urgency, cover_page, cover_page_price, remark, owner_name, is_admin_print, bound_owner_name, source, download_url, count, take_orders`

### 1.4 状态回报 ⚠️ 注意通道不对称

**这是最容易踩的坑：接受/打回/放弃是 HTTP，而"开始打印/成功/失败/页数"只有 SocketIO，没有 REST 版本。**

| 动作 | 通道 | 接口 | 效果 |
|---|---|---|---|
| 接受订单 | HTTP | `POST /api/accept_order` `{order_id}` | `printing → accepted`，刷新 `locked_at`。订单已取消 → **409 拒绝** |
| 打回订单 | HTTP | `POST /api/reject_order` `{order_id}` | `queued/printing → rejected` |
| 放弃订单 | HTTP | `POST /api/abandon_order` `{order_id}` | 未打印的子任务 → `abandoned` |
| 放弃预留单 | HTTP | `POST /api/abandon_reserved_order` | 同上（预留单场景） |
| 文件下载完 | **SocketIO** | emit `file_ready` `{order_id, task_ids}` | 预约单 `downloading → waiting` |
| 开始打印 | **SocketIO** | emit `start_printing` `{task_ids}` | 记录服务器权威的 `print_started_at`；`waiting/downloading → printing` |
| 打印成功 | **SocketIO** | emit `print_success` `{task_id, copies, duplex, page_range, page_count, owner_name, is_admin_print}` | → `sent`；同步实际配置并**重算价格** |
| 打印失败 | **SocketIO** | emit `print_fail` `{task_id, error}` | → `failed`，`reject_reason` 写失败原因 |
| 页数结果 | **SocketIO** | emit `page_count_result` `{file_id, page_count, orientation, success}` | 写入 `files.page_count` + MD5 索引复用 |
| 页码范围截断 | **SocketIO** | emit `page_range_truncated` | 提示用户实际范围被截断 |
| 心跳 | **SocketIO** | emit `ping` → 服务端回 `pong` | 刷新在线判断（90s 内算在线）。HTTP 拉单入口也会刷新 |
| 断线延迟下载 | **SocketIO** | emit `download_delayed` `{order_id}` | 文件未就绪时报"延迟"；服务端回 `download_delayed_ack` |

⚠️ **来源校验**：`print_success` / `print_fail` / `start_printing` 都校验"该子任务的 `operator_client` 是否等于当前连接的 `client_id`"，不符直接静默丢弃。所以设备端**必须保持同一个 `client_id`**，且回报要走**同一条 SocketIO 连接**。

### 1.5 文件与页数

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/download/<file_id>?t=<签名>` | **签名有效 3600 秒，过期即 403，目前没有任何重签接口** |
| GET | `/api/file_page/<file_id>?target_client_id=` | 轮询页数（PDF 服务端可自数；Word/md 需设备端转换回报） |
| POST | `/api/cancel_page_analysis` | 取消页数分析 |
| GET | `/api/pricing` | 定价（权威） |
| GET | `/api/orders` / `/api/order/<id>` / `/api/order_price/<id>` | 订单查询与报价 |

页数分析是**按需下载、临时转换**：设备端下载 → 转 PDF → 数页 → 回报 → 服务端写 `files.page_count` + MD5 索引全站复用。

### 1.6 排障

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ping` | 存活 |
| GET | `/api/printer_status` | 打印机在线状态 |
| POST | `/api/log/report` | 设备端上报日志 |
| GET | `/api/log/fetch` | 拉取指定设备日志 |
| POST | `/api/log/collect_all` | 向所有在线设备推 `request_log` 收集日志 |

## 2. 现有状态机（`order_files.status`）

```
scheduled → downloading → waiting → printing → accepted → sent
                                                          ↘ failed / offline_unknown
                                                          ↘ rejected / abandoned / canceled
```

父订单状态由子任务聚合（`aggregate_order_status`），优先级：

`failed(9) > printing(8) > waiting(7) > accepted(6) > downloading/offline_unknown(5) > scheduled/queued(4) > sent(3) > abandoned(2) > rejected(1) > canceled(0)`

**现有超时/回收机制（对他的模型全是致命的）：**

| 机制 | 周期 | 行为 | 对他的影响 |
|---|---|---|---|
| `check_printing_timeout` | 60s | `accepted` 超过 `PRINT_FEEDBACK_TIMEOUT=180s`（3 分钟）→ `failed` | 攒单期间任务判失败 |
| `recover_orphaned_printing_tasks` | 2min | `printing` 超过 5 分钟 → 回退 `queued` **重新下发** | **可能重复打第一面 → 纸叠报废** |
| `check_printing_timeout` | 60s | `offline_unknown` 超过 `OFFLINE_UNKNOWN_TIMEOUT=1800s`（30 分钟）→ `failed` | 设备关机/断网过夜即判失败 |
| `on_disconnect` | 实时 | 名下 `printing` → `queued`；`accepted` → `offline_unknown`；`downloading` → `scheduled` | 断线即丢绑定关系 |

另有两条已存在的宽容规则，可参考口径：
- 未 accept 的 `printing` **不判失败**，只停止计时（`ACCEPT_WAIT_TIMEOUT=600s`）后等孤儿回收；
- `print_success` 的允许来源状态集**包含 `failed`**（注释写明是为缺纸/卡纸的 3 分钟误判兜底）——这是现有"迟到成功可救回"的机制，**他的等待时长远超 3 分钟，靠这个只能兜结果、不能解决等待期间显示"失败"**。

## 3. 他需要的新增接口 / 服务端改动

按必要程度排序。**R1–R5 不解决，他的模型无法工作。**

### R1　独立设备端 token【必须】

- **现状**：全局唯一 `TOKEN`，无法单独吊销/限权，且与他自己的设备混在一起。
- **接口**：
  - `POST /api/printer/token/create`（管理员）→ `{token, client_id, label, scopes, expires_at}`
  - `POST /api/printer/token/revoke` `{token}`
- **建议**：`device_tokens` 表（`token` 只存哈希、`client_id`、`label`、`created_at`、`revoked_at`、`scopes`）；鉴权处**同时接受全局 TOKEN 与新表 token**（零回归）；轮换时允许新旧并存窗口。
- **需他定**：是否需要按接口限权（如只允许拉单+回报，不允许改能力/删设备）。

### R2　"第一面已打、等第二面"状态 + 全套豁免【必须，整个模型的地基】

- **新状态**：`pass1_done`（等价于原需求书的 `awaiting_flip`，但他的语义更宽：跨订单累计、无限期）。写入 `order_files.batch_id`（设备端生成，仅存档/排障用）。
- **进入**：SocketIO `pass1_done` `{task_ids: [...], batch_id, sheets, printed_at}`（或 REST `POST /api/device/pass1_done`）
- **退出**：`print_success`（第二面完成，逐个 task 回报）／`print_fail`
- **必须同时改的 5 处**（缺一即出事故）：

| # | 位置 | 要改成 |
|---|---|---|
| 1 | `check_printing_timeout` 的 `accepted` 3 分钟判定 | `pass1_done` 不参与 |
| 2 | `recover_orphaned_printing_tasks` 的 5 分钟回退 | `pass1_done` 不参与（**否则重复打第一面**） |
| 3 | `offline_unknown` 30 分钟判定 | `pass1_done` 不参与 |
| 4 | `on_disconnect` 回滚 | **`pass1_done` 绝不能被回滚成 `queued`**（保持绑定 `operator_client`） |
| 5 | `print_success` / `print_fail` 的来源状态白名单 | 加入 `pass1_done` |

- **还要改**：`_STATUS_PRIORITY` 与 `aggregate_order_status` 加入新状态（建议优先级低于 `accepted`，因为它是"半成品在途"而非"正在打印"），并让**移动端订单列表/订单详情能显示"第一面已打，等第二面"**——否则用户会看到订单长期停在某个奇怪状态。
- **计费口径**：只有第二面完成才 `sent`。等待期间既不能计成已完成，也不能计成失败（`pass1_done` 天然满足，需要在统计查询里显式排除）。

⚠️ **产品语义副作用（必须由他确认能否接受）**：订单的完成时机从"提交后几分钟"变成"他回家翻面之前"，而订单上挂着**加急费 / 派送费 / 无障碍预约承诺**。

- **加急**：用户付了加急费，单子却要等几小时甚至过夜才完成 —— 加急的意义消失；
- **派送**：派送以订单完成为触发点，等于把派送时间也一起推迟；
- **无障碍/预约**：原本承诺"到点自动完成"，现在变成"到点只打一半"。

因此 `flip_mode=accumulating` 应当**限定适用条件**（例如仅允许"自行到店自取 / 无加急 / 无派送"的订单进入积单模式），或在下单时就明确告知"本单需一次人工翻面后才能完成"。否则是对付费用户的承诺违约 —— 这也是现有系统宁可 409 拦下、也不放行"无人值守双面"的原因。

### R3　"待打第二面"清单查询【必须】

```
GET /api/device/pending_pass2?client_id=<id>
→ { success, count, tasks: [{
      task_id, order_id, order_number, file_id, file_name, source_md5,
      copies, duplex, page_range, page_count, image_orientation,
      batch_id, pass1_seq,      # 设备端上报的全局叠序（服务器原样存回）
      pass1_done_at }] }
```

- **用途**：设备端重启 / 换机 / 本地账本损坏后**重建第二面批次**；以及自建页面展示"攒了多少张、都是谁的单"。
- **注意**：服务器返回的清单**只能用于对账**，第二面的**叠序仍以设备端账本为权威**（§0）。

### R4　下载链接重签【必须 —— 在他的模型里从 P1 升为 P0】

- **现状**：签名 `max_age=3600`，**无重签接口** → 只能"pass A 时把源文件永久缓存"，一旦缓存被清/换机/重打就废单。
- **接口**：`GET /api/device/task/<task_id>/download_url?client_id=` → 返回新签名 URL（也可同时提供 `GET /api/device/file/<file_id>/download_url`）。
- **建议顺带**把设备端签名时长做成服务端可配（如 7 天），并保持 `/api/download/<file_id>` 的 1 小时旧签名兼容。

### R5　取消 / 放弃的通知与语义【必须，否则物理错位】

- **现状**：用户取消订单时服务端 emit `order_canceled` `{order_id, ...}`（仅在线时送达），官方本地工具据此撤回未打的标签页。
- **他的特殊问题**：**第一面已出纸的订单被取消时，那张纸已经在他的叠里**。第二面批次必须**仍然为它送一张纸**（背面留空或打标记），否则后面全部错位一页。
- **必须二选一并写进文档**：
  - (a) `pass1_done` 的任务**拒绝取消**（`/api/cancel_order` 返回 409 + "第一面已出纸，请完成第二面"）—— 简单、安全；
  - (b) 允许取消，状态转 `pass1_done_canceled`，**仍留在 `/api/device/pending_pass2` 清单里**，由设备端在背面留空 —— 灵活，但要求设备端严格遵守。
- **离线补偿**：设备端重连后要能查到"等待期间被取消的订单"（建议 `pending_pass2` 里带 `canceled` 标记，或补一个 `GET /api/device/canceled_since?ts=`），不能只依赖"当时在线收到事件"。

### R6　能力语义扩展 `flip_mode`【必须，但**只改服务端无效**】

- **他需要**：`flip_mode = accumulating`（无人值守打第一面 → 跨订单累计 → 一次人工确认后打全部第二面）。现有 `auto_duplex=false` 会被拦。
- **现状拦他的地方共 5 道**：

| # | 位置 | 说明 |
|---|---|---|
| 1 | 服务端 `_device_needs_manual_flip` / `check_auto_print_duplex_conflict`（`app.py:966/975`，由 `submit_order` 调用） | 无障碍/预约 + 双面 → **409** |
| 2 | 服务端 `printer_capability` / `_printer_probe_from_request` 字段 | 只有 `auto_duplex` 三态，无 `flip_mode` |
| 3 | **小程序 4 个入口**（`h_n_print/pages/index/index.js` 1986 切设备 / 2025 选双面 / 2275 开无障碍 / 2856 提交兜底） | 本地判 `auto_duplex === false` → 弹 toast，**请求到不了服务端** |
| 4 | **APP 4 个入口**（`android_app/www/print.js` 711 / 1252 / 1752 / 1942）+ 设备列表文案（`www/app.js` 1343） | 同上 |
| 5 | 官方本地工具的无人值守挂起（`gui.py:6036/6046`） | 与他无关，但口径要一起改才不矛盾 |

- ⚠️ **必须让他知道**：他要求"不被无障碍拦掉"同时"不改小程序/APP 源码"，**这两条互斥**。两条路：
  - **(a) 改移动端**：4+4 处口径改为 `auto_duplex === false && flip_mode !== 'accumulating'` 才拦。**需要发小程序 + APP 新版本。**
  - **(b) 不动移动端**：把该设备云端能力留成 `null`（移动端只认 `=== false`，服务端也放行）。**代价**：设备列表不再显示「🖐 需人工翻纸」，下单时也不再有任何"这单需要人翻一次纸"的提示 —— 等于**不告知用户**。这是有产品风险的旁路，不是"等价方案"。

### R7　批次标识【建议】

- `batch_id` 由**设备端生成**（服务器不需要理解其语义），上报时随 `pass1_done` / `print_success` 带上，服务端存 `order_files.batch_id` 供排障与对账。
- ⚠️ 他的第二面批次**跨多个订单**，所以 `batch_id` **不能**当作父订单标识 —— 只能是"这一叠纸"的标识。

### R8　进度上报【可选】

- SocketIO `pass1_progress` / `pass2_progress` `{task_ids, done_sheets, total_sheets, text}`，服务端存字段供小程序展示"第一面 37/120 张已完成，等待翻面"。
- 他若按原计划在局域网自建页面展示，可以不加；但**服务端没有任何字段能表达"在途进度"**，不加就只能在自建页面看。

### R9　接口文档 + 版本头【必须】

- 仓库目前**只有 `DEPLOY.md`，没有设备端 API 文档**。需要一份正式说明，至少包含：本文 §1 的通道不对称、§2 的状态机与超时表、鉴权方式、错误码。
- 请求头 `X-Device-API: 1`；破坏性变更（字段增删、状态语义、超时阈值）提前告知。

## 4. 他自己必须负责的部分（服务器帮不了）

1. **叠序账本（最重要）**：第一面每打一张都要记录 **全局序号 + 属于哪个 task / 哪一份 / 哪一页**。第二面必须按**第一面全局序列的逆序**打印（整叠原样放回、进纸盒从最上面取纸）。跨订单累计后，这个账本是唯一真相，**不能拿服务器的任务列表当依据**。
2. **空白占位**：单面任务、奇数页的末张、已取消但仍占位的纸，都必须在第二面批次里**各占且只占一个槽位**（背面留空或打标记）。漏一个，后面全错位。
3. **源文件持久化**：第二面可能隔夜/隔天才打。在拿到 R4 之前，他必须把第一面用过的源文件（或转换后的 PDF）**永久缓存到用户数据目录**，不要放 `%TEMP%`（系统清理/安全软件会删，这是官方工具踩过的坑）。R4 到位后可放宽。
4. **180° 旋转补偿与长/短边规则**：必须按"**同一叠纸**"验证，不能按单订单验证（官方工具实测：长边补偿、短边不补偿；他家 1020 需实机标定）。
5. **半成品纸叠的物理保全**：出纸槽会被别人拿走、混进其他打印件，而第二面必须接着**同一叠**打。建议常驻提示 + 打印一张"请勿取走"说明页 + 遵守出纸盒容量上限（他的用例 10：>90 张需切分）。
6. **幂等**：断网重连后不得重复回报、不得重复打第一面。
7. **超容量批次切分**：每组必须能独立成立正确的叠序，且组标签清晰。
8. **SocketIO 客户端**：必须实现（`python-socketio`），否则无法回报结果（§1.4）。

## 4.5 设备端资源硬约束（内存 / GDI / 后台处理程序）

"跨订单积单、一次打完全部背面"意味着**单批可能有几百到上千面**，这是官方本地工具从未面对过的量级（它受出纸盒 100 张限制，一批最多约 100 张）。因此下面是**硬性验收项**，不是建议。

### 实测数据（`python tests/verify_render_memory.py --pages 1000 --dpi 300`）

官方管线（`pdf_printer.print_plan_pass` 逐页段：`get_pixmap → Image.frombuffer → transpose → ImageWin.Dib`，去掉出纸那一步）：

| 指标 | 300 dpi（标清） | 400 dpi（官方默认） |
|---|---|---|
| 单页位图（A4） | 2480×3509 = **24.9 MiB** | 3306×4678 = **44.2 MiB** |
| 长跑工作集漂移 | **1000 面 +2.9 MiB（+0.12 个单页位图）** | 300 面 +0.8 MiB |
| 稳定工作集 | ≈ 140 MiB | ≈ 199 MiB |
| 单页流水线瞬时峰值 | ≈ **5.7 个单页位图**（≈142 MiB） | ≈ 5.7 个（≈252 MiB） |
| GDI 句柄 | **0 → 2，不随页数增长** | 0 → 2 |
| 速率 | 19.3 面/秒 | 11.0 面/秒 |

**对照档（故意持有渲染结果）**：同样 300 dpi，只持有 49 面就吃掉 1.22 GiB，工作集线性上涨（+996 MiB / 40 面），60 面需 1.5 GiB。

### 结论：管线本身 O(1)，"堆积"只可能来自设备端自己的代码

> **逐页渲染 + 立即释放是安全的**（1000 面漂移 0.12 个单页位图，GDI 句柄不涨）。会堆积的只有一种情况：设备端**自己持有**渲染结果 —— 把 `pix` / `img` / `Dib` 存进队列、账本、缓存或"待打印页缓冲"。**这件事必须由设备端自己证明不会发生。**

### 必须遵守的 6 条

| # | 约束 | 原因 |
|---|---|---|
| M1 | **逐页渲染、立即释放**；禁止在任何容器里持有 `pix`/`img`/`Dib` 引用 | 单页 25~44 MiB，持有 100 面即 2.5~4.4 GiB |
| M2 | **跨订单合并必须落盘**（临时 PDF 文件），禁止在内存里 `insert_pdf` 拼接整批 | 内存合并 = O(总页数)。官方做法是写 `%TEMP%\hn_duplex_batch_*.pdf` 再逐页渲染 |
| M3 | **一个打印作业不要放几百面**：按 50~100 面用 `StartDoc`/`EndDoc` **分段提交**，中途**不要动纸叠**（进纸盒连续取纸，叠序天然保持） | 后台处理程序体积 ≈ 面数 × 单页位图：500 面 @300 dpi ≈ **12 GiB**，足以撑爆 `spool\PRINTERS` 或让作业"卡在 XX%"。**这是他模型里最可能的真实上限，必须真机实测** |
| M4 | **空白占位页不要按打印机原生 DPI 开位图** | 原实现按 `GetDeviceCaps(HORZRES/VERTRES)`（**设备像素**，非 PDF 点数）开整页 RGB 图，600 dpi 下实测 **99.6 MiB/张、每张还占 2 个 GDI 句柄**（20 张 = 1992 MiB / +40 句柄）。**官方工具已修复**：复用一个 8×8 纯白 DIB 拉伸到整页 → 与张数无关（20 张 = 0.0 MiB / +2 句柄）。他的模型里空白占位极多（单面任务、奇数页末张、被取消仍占位的纸），**不得重新引入旧写法** |
| M5 | **不要部署 32 位进程；若坚持，必须自己按位宽重定像素上限** | 400 dpi 单页流水线瞬时峰值 ≈ 252 MiB，叠加 Office COM 转换（Word 转换自身常占数百 MB）在 2 GiB 地址空间里很危险。官方工具原来的 `MAX_RENDER_PIXELS` 是硬编码 4 亿像素，注释却写"约 32 位进程上限"—— 400 Mpx × 3 字节 = **1.14 GiB 单缓冲**，乘实测 5.7 倍瞬时系数 ≈ 6.5 GiB，**对 32 位等于没有保护**。**官方已改为按位宽分档**（`max_render_pixels()`）：64 位 ≈ 94 Mpx（269 MiB 单缓冲）、32 位 ≈ 18 Mpx。他可照抄这个口径，但**不要**只抄那个数字 —— 要抄"按可接受瞬时峰值反推"的方法 |
| M6 | **每打完一组就 `doc.close()` 重新 open**，不要用一个 `fitz.Document` 打上千面 | MuPDF 会缓存已访问的 Page 对象；官方是在 `finally` 里 `doc.close()` |

### 一条被实测否掉的"优化"（避免他也走一遍）

曾考虑把第二面的 `img.transpose(ROTATE_180)` 改成渲染期 `fitz.Matrix(...).prerotate(180)`，
以省掉一次整页位图拷贝。**实测后否掉**（`python tests/verify_render_memory.py --prerotate-check`）：

| 维度 | 实测结果 |
|---|---|
| 像素 | **非等价**：0.56% 像素不同（仅落在抗锯齿边缘、涉及 120/3509 行，最大差 34/255）。不是错位、不是方向错，视觉不可辨，但**不是逐字节等价** |
| 内存 | **无收益**：分进程测进程峰值 **141.9 vs 142.0 MiB**（300 dpi / 200 面）。页内峰值由 MuPDF 渲染内部缓冲区主导，transpose 只占 ~1/5.7，被更大的水位掩盖 |
| 耗时 | 每页省一次 26 MiB 整幅拷贝（约 13~20 ms/面，300 dpi 渲染吞吐 +26%）。但打印每面要 1~4 秒，**渲染耗时被打印机物理速度掩盖**，批次里收益≈0 |

**结论：不要做。** 收益为零、却要改一条已在实机验证过、且第二面方向只有打出来才知道的路径。
（他若在别处看到"渲染期旋转省内存"的说法，这里的数就是反例。）

### 验收方式（写进对接验收，不通过不予结算）

```bash
python tests/verify_render_memory.py --pages 1000 --dpi 300   # 漂移 < 3 个单页位图、GDI 增量 ≤ 5
python tests/verify_render_memory.py --pages 300  --dpi 400
python tests/verify_render_memory.py --blank-check             # 空白页成本应远低于官方 99.6 MiB/张
python tests/verify_render_memory.py --pages 60 --dpi 300 --hoard   # 对照档：看清红线在哪
```

设备端还需两项**真机**自测（本脚本覆盖不到）：
- **spool 监控**：连续提交 500 面作业，盯 `C:\Windows\System32\spool\PRINTERS` 峰值体积与作业是否卡住；
- **长跑**：连续 2000 面后工作集仍在同一量级，且打印队列无残留作业。

## 6. 需要共同确定的问题

1. **账本权威**：待打第二面以设备端为权威（本文推荐）还是服务器为权威？
2. **取消语义**：第一面已出纸的订单被取消 —— 拒绝取消（R5-a）还是允许但背面留空（R5-b）？
3. **父订单完成时机**：同一订单的文件被切分到不同翻面组时，父订单何时算完成（全部子任务 `sent` 才完成？）
4. **`flip_mode` 落地方式**：改移动端发版（R6-a）还是云端能力留 `null`（R6-b，不告知用户）？
5. **等待时长上限**：无限期等待，还是 N 天后超时置 `failed` 并提示人工处理？
6. **独立 token 与限权**：是否需要按接口限权（只允许拉单 + 回报）？
7. **进度文案**：是否需要服务端字段（R8），还是他自己在局域网页面展示就够？

## 附：一句话总览

> 现有 API 只差 **5 项**就能支撑他的模型：**独立 token（R1）、`pass1_done` 状态 + 四处超时/回滚豁免（R2）、待打第二面清单（R3）、下载重签（R4）、取消语义（R5）**；另有能力语义（R6）需要他与移动端发版一起决定。
> 而"第一面出纸后整叠纸的顺序与保全"**完全由设备端负责**——这部分服务器无论怎么改都替代不了。
