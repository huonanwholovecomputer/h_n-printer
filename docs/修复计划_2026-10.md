### A2 · 🔴-2 `on_disconnect` 不校验 sid → 重连后旧连接把新连接正在打的任务回滚

- **位置**：`app.py:2886-2894`（删除分支）；三处回滚 SQL `:2830-2841` / `:2847-2857` / `:2862-2876` 只按 `operator_client` 过滤；对照 `:2761-2770`（连接时已按 sid 替换）
- **根因**：`:2764` 的注释自己写明"旧连接断线回滚会按 sid 反查兜底"，但 `:2887` 先整体 `del printer_clients[client_id]`，`else` 里的 sid 兜底在 client_id 存在时**永远不可达** —— 作者意图与实现相反。
- **修法**：
  1. 删除分支改为"只有 sid 匹配才认领"：
     ```python
     with printer_clients_lock:
         cur = printer_clients.get(client_id)
         if cur is not None and cur.get("sid") != request.sid:
             return          # 旧连接的 disconnect，不得删新连接、也不得回滚
         if cur is not None:
             del printer_clients[client_id]
         else:
             ... 现有 sid 兜底 ...
     ```
  2. 三处回滚 SQL 加 sid 守卫（`AND operator_client = ?` 之外再校验该任务确实由**本条连接**的 sid 领取），或把回滚整体移到 `return` 之后的路径上，保证"被替换的旧连接不回滚"。
- **验收**：新增探针脚本 —— 同一 `client_id` 连两次（sid A → sid B），令 A 断开，断言：注册表仍指向 B、B 名下 `printing` 任务**未被**回滚、A 名下任务正常回滚。
- **风险**：中（改的是接单状态机入口）。**联动 G-🟡1**：`cloud_client.py:639-797` 的 `status_queue.json` 读-改-写无锁 —— 同属"上报丢失 → 重推 → 重复打印"，本轮一并修（加锁覆盖整个 RMW）。

### A4 · 🔴-7 配置被写坏即无法启动

- **位置**：`printer_config.py:771`（`except (json.JSONDecodeError, OSError, ValueError)`），触发点如 `:76` `float(data.get("cover_page_price", 0.10))`、根节点为数组时的 `data.get`
- **根因**：键存在但值为 `null` 时 `.get` 返回 `None` 而不取默认 → `float(None)` 抛 **TypeError**；根节点是数组 → **AttributeError**。两者都不在捕获列表。而 `load()` 是 `MainWindow.__init__` 第一条语句（`gui.py:2437`）且外层无保护 ⇒ **启动即崩**。
- **修法**：`except` 补 `TypeError, AttributeError`（兜底）；**并**在 `from_dict` 里对数值字段做 `_num(value, default)` 归一（根治，避免"备份成 .corrupt 后丢全部配置"）。两级一起做：先归一，归一不住再兜底。
- **验收**：新增断言 —— 3 份坏配置依次喂 `load()`：① `{"cover_page_price": null}` ② `[1,2,3]`（数组根） ③ 截断 JSON；三者都必须返回默认配置且**不抛异常**。
- **风险**：低。

### A5 · 🔴-11 推送失败分支无条件盲写 `queued` → 刚判定的 `rejected` 被自己撤销

- **位置**：`app.py:5123`（`conn.execute("UPDATE order_files SET status = 'queued' WHERE id = ?", ...)`）
- **根因**：该 `else` 分支**没有 `AND status='printing'` 守卫**。而 `push_print_task_to_client` 在 `rowcount == 0`（任务已非 `queued`，例如刚被判 `rejected`）时同样返回 False（`:2354-2362` 打 `[SKIP]` 后 return False）⇒ 越界文件被改回 `queued` → 30 秒后照常推送 → **越界文件被真实打印**，顾客看到"排队中"而不是"被打回"。
- **修法**：`... SET status = 'queued' WHERE id = ? AND status = 'printing'`（首选），或直接删掉该分支交给函数内部已有的回滚。
- **验收**：脚本 —— 构造 `page_count_verified=1` 且 `page_range` 越界的订单，走 `submit_order`；断言文件终态为 `rejected`（**不是** `queued`）、`reject_reason` 保留。
- **风险**：低。

### A7 · 日志诊断② 图片 PDF 缓存 key 写读不一致 → 缓存 100% 失效

- **位置**：写侧 `gui.py:9069-9071`（用 `job.engine`，`"word"`/`"wps"` 都加后缀）；读侧 `gui.py:5747-5748`（**只对 `.docx` 加后缀**）
- **根因**：图片的 `job.engine` 默认就是 `"word"`（`gui.py:9432-9439` 只对 `.doc/.docx` 改引擎）⇒ 写 `md5_eword`、读 `md5` → **永不命中**。磁盘实证：`pdf_cache/index.json` 32 条里，带 `_eword` 的 12 条全是本地拖入（读不到），无后缀的 12 条来自云端下载（能命中）——恰好解释"云端不反复转换、本地拖入才反复转换"的分裂现象。

- **风险**：低。**联动**：历史脏缓存（带 `_eword` 的图片条目）修完即失效，做一次性清理（读不到的条目本来就无用）。

### A8 · 日志诊断② `_add_files` 每次添加遍历全列表预转换（O(n²)）

- **风险**：低。
